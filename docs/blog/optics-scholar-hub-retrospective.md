# 用 AI 做一个真正能用的科研导航：光研导航的完整开发复盘

找一本合适的期刊，或者确认一场会议还能不能投稿，经常需要在多个网站之间来回跳转。期刊主页、作者指南、分区查询平台、会议征稿通知和注册页面，各自提供一部分信息，却很少按照研究生的实际使用顺序组织起来。

我想做的，就是把这些入口和关键事实整理到一个地方：能按研究方向查找光学相关期刊，也能查看会议的投稿截止、举办时间和具体要求。于是，我借助 AI 开发了一个开源网站——**光研导航（Optics Scholar Hub）**。

- [在线访问光研导航](https://uestczhaoyan-gif.github.io/optics-scholar-hub/)
- [GitHub 源代码与数据](https://github.com/uestczhaoyan-gif/optics-scholar-hub)

从仓库中 2026 年 9 月 10 日的首个提交，到 10 月 6 日完成 V1.0 验收，再到 10 月 9—10 日的一轮使用体验改进，这个项目经历了大约一个月的迭代。这里的时间跨度不等于连续开发工时；这篇文章也不会用没有记录的数据估算 AI 节省了多少时间。

真正值得复盘的是：AI 帮我把网站做出来之后，怎样让它逐步成为一个能查、能解释、能维护，也能明确结束一轮建设的工具。

## 1. 起点：先解决查找问题

项目的灵感之一来自 CCF-Deadlines：用结构化数据整理会议，让截止时间更容易查找。但光学领域有自己的特点，不能直接照搬计算机领域的会议评价方式。

光学研究可能同时涉及材料、电子、物理、化学、生物医学和计算成像。同一个研究方向，既可能对应光学专刊，也可能出现在综合性或交叉学科期刊中。会议的发表形式同样不统一：有的收完整论文，有的收摘要，有的有独立的最新成果通道，还有的只是展览或产业论坛。

因此，我把网站定位成中文学术导航，最初希望回答四类问题：

1. 我的研究方向可能适合哪些期刊？
2. 哪些会议已经公布投稿安排，截止时间是什么？
3. 投稿前需要准备什么，应该去哪里查原始要求？
4. 页面上的信息来自哪里，什么时候核对过？

最后一个问题后来成为整个项目最重要的约束。网站收录多少条信息固然直观，但读者能否判断这些信息的适用范围，更决定它有没有实际价值。

## 2. 先搭一个能够发布的最小系统

初版围绕会议目录、期刊目录、投稿入门和开源维护展开。技术上采用 React、TypeScript、vinext 静态导出，配合 Tailwind CSS、shadcn 与 Base UI 组件，数据独立保存在 JSON 文件中。

项目没有站内账号、数据库和运行时 AI 接口。访客打开页面后，搜索和筛选主要在浏览器里完成；关注列表保存在当前浏览器中。

这个选择与项目的需求有关。对于一个以公开资料查阅为主的目录，先把数据结构和浏览体验做好，比一开始就增加服务器、用户系统和后台管理更切合实际。JSON 也方便通过 Git 查看具体变化：哪场会议改了哪项日期，哪本期刊补充了哪条来源，都能留下差异记录。

最终的组织大致如下：

```text
data/                 期刊、会议、系列、活动及公共词表
app/、components/     页面、卡片、筛选和交互组件
lib/                  日期、分区、检索、分享与日历等逻辑
scripts/              数据校验、覆盖报告和来源巡检
tests/                关键规则的自动测试
docs/                 规划、证据、回归和维护记录
.github/workflows/    自动检查与 GitHub Pages 发布
```

AI 在这一阶段承担了代码编写、组件组合、脚本和文档整理等工作。我主要给出使用需求，检查结果，并不断补充光学场景中容易被遗漏的区别。一个能打开的页面建立起来后，后续的问题才开始变得具体。

## 3. 最费判断的部分，是学术信息怎样表达

### 分区必须带上版本和学科

如果把期刊简单写成“一区”或“二区”，读者很容易把不同评价体系混在一起。项目因此将 JCR 与中科院分区分开保存和筛选，同时保留版本年、学科和来源。

JCR 记录还区分版本年与指标年；中科院记录区分大类和小类。一条学科的分区，不能自动代表这本期刊在其他学科下的结果。

证据也有区别：官方披露、依据已知排名推算，以及第三方公开参考，不能在界面上显示成同一种确定程度。没有核实到某个版本，页面就应当保留未知，而不是把旧版本当成今年的数据。

### 索引与分区是两组信息

SCI/SCIE、ESCI、EI 与期刊分区被放进不同的数据字段。期刊有影响因子，不能据此直接断言其当前属于哪个具体索引；出版社的收录声明和数据库查询结果，也需要分别注明证据方式。

后续核验开始使用 ISSN 和 eISSN 核对身份，并记录 Compendex 来源表或 Clarivate Master Journal List 查询依据。这减少了同名、近似刊名及不同出版载体带来的混淆。

这里仍有一个边界：期刊在来源表中出现，不代表某篇论文已经被检索。网站能够提供来源和查证入口，不能代替单篇检索结果。

### 日期精度决定了能显示什么

会议通知经常只公布某一天，没有具体时刻或时区。如果程序自行补成当天 23:59，再显示精确到秒的倒计时，表面上更完整，实际却加入了原文没有提供的信息。

项目把时间分成三种情况处理：有明确时区的精确时间、仅日期，以及尚未公布。只有证据足够时，才进行精确时间转换；日期级信息保留日期级提示，未知字段使用 `null`。

同样，普通论文、摘要、PDP、录用通知、注册和终稿是不同事件。投稿状态必须结合事件类型判断，不能把“未来还有一个日期”直接解释成“现在还能投稿”。

这套规则让数据模型变得复杂了一些，却避免了科研导航中很容易误导使用者的几种表达。

## 4. 扩充目录时，先管理候选和证据

网站逐渐从核心光学方向扩展到材料、电子、物理、生物医学和计算交叉领域，也完成了我指定的 54 本期刊清单的收录。

但名单一旦开始扩充，就会出现新的问题：搜索到的名字是否真的是同一本刊？一个会议网页是否对应当前届次？某个高影响力综合期刊与光学研究有什么实际联系？

项目为此增加了候选管理。候选可以进入正式目录，也可以保持待核实或暂缓。状态变化需要有依据，不能为了让数量好看就全部标为已收录。

对部分交叉期刊，还补充了实际发表论文的范围样例，帮助读者理解它为什么与光学有关。这些样例只说明研究范围，不保证类似稿件会被接收，也不能作为分区或索引证据。

核验中遇到的访问限制也要被记录下来。官网返回 403、页面要求登录或出现安全验证，都不意味着可以让 AI 用记忆补齐。已有证据支持到哪里，记录就写到哪里；缺少的字段和后续触发条件继续保留。

我从中得到的一条经验是：**给 AI 一个可以合法表达“不知道”的数据结构，比要求它把每个空格填满更有用。**

## 5. 从单届会议走向系列与往届

早期会议卡片主要回答“这一届什么时候投稿”。随着使用场景变多，我又希望查到往届信息，以及下一届是否已有公告。

这需要将“系列”与“届次”分开。例如，一个稳定系列可以关联多个年份的会议，但每届必须拥有自己的日期、地点、投稿要求和官方来源。不能把旧记录的年份改一下，就当成新届次。

后来网站增加了系列与往届页面、系列关注，以及从单届卡片跳转到历届记录的入口。已结束会议继续保留，尚未公告的下一届则明确未知，不按往年规律推算。

与此同时，展览和论坛被放进独立目录。有些活动与光学行业高度相关，但没有论文征稿依据；把它们硬塞进会议投稿模型，只会生成并不存在的截止时间。

这次调整说明，导航是否清楚，很大程度上取决于对象有没有分对：系列和届次、论文会议和展览、投稿截止和注册截止，都需要各自的位置。

## 6. 让信息查完之后还能继续使用

基础目录形成后，功能建设开始围绕访问者的后续动作展开。

| 使用需求               | 实现方式           | 保留的边界                         |
| ---------------------- | ------------------ | ---------------------------------- |
| 下次继续看感兴趣的条目 | 浏览器本地关注     | 不提供账号同步                     |
| 把筛选结果发给同学     | 分享并恢复筛选链接 | 不传递个人关注列表                 |
| 把会议安排放进日历     | 导出 `.ics` 文件   | 导出的是快照，不会自动订阅后续修改 |
| 判断是否有新版数据     | 检查已发布目录版本 | 不代表此刻重新核验了所有官网       |
| 知道优先维护哪些条目   | 生成维护与覆盖报告 | 队列数量不等于错误数量             |

这些功能都没有改变静态网站的基本架构，却让目录可以接入实际工作流程。

其中一个容易忽略的设计是数据版本。构建时生成的 `catalog-version.json` 包含目录摘要和构建时间，可以帮助判断浏览器中的数据是否与已发布版本一致。但构建时间与事实核验时间分属两个层面：今天重新发布网站，不意味着所有期刊和会议今天都被重新核对过。

## 7. 自动化负责发现变化，事实更新仍要经过审核

会议日期会调整，作者指南会改版，网页也可能失效。如果只能依赖维护者逐页打开检查，长期维护会很困难。

项目配置了每日来源巡检，按计划在北京时间约 09:23 执行，实际运行可能延迟。它检查访问状态和内容指纹，并把变化关联回受影响的条目和字段。后续又覆盖了显式图片与 PDF 来源的字节变化。

不过，网页指纹变化只是一条核验信号。主办方可能调整了页脚，也可能真正修改了投稿日期；自动访问失败也可能只是限流或访问控制。

因此，维护流程保留了审核环节：

```text
来源巡检发现变化
        ↓
阅读相关官方通知，确认实际变化及适用范围
        ↓
修改对应数据字段，记录核验依据
        ↓
校验、测试、构建、提交和部署
        ↓
访问者加载已审核发布的新版本
```

这一点也适用于 AI：它可以帮助定位资料、整理差异和执行修改，但抓取成功、生成一段流畅说明，都不能单独证明学术事实已经核实。

## 8. 一个重要转折：给项目规定终点

目录项目很容易陷入持续扩充。补完几本期刊，又发现更多候选；核完一批会议，又有下一届公告。即使每天都有进展，也可能始终回答不了“这个版本什么时候完成”。

到 10 月 5 日，项目开始固定 V1.0 的范围和验收门槛。冻结时的目录包含 104 本期刊、133 届会议、98 个系列和 10 项展会或论坛，并从已有候选中确定需要完成审查的 60 项。

验收覆盖六个方面：功能可用、正式条目质量、固定候选审查、交叉期刊范围样例、核心系列时间深度，以及发布和维护交接。

固定范围不是停止修正问题，而是把当期必须做完的工作写清楚。后续新发现的候选进入下一轮，不再自动增加本版的完成条件。

到 10 月 6 日，固定 60 项候选全部完成实际审查，其中 8 项准入，52 项保留已经记录的限制。V1.0 最终目录达到 112 本期刊，完成 32 项自动测试以及对应的界面和发布验收。

这里的“审查完成”并不意味着所有字段都变成已知。一个条目可以已经被认真检查，同时仍然缺少公开可访问的分区依据或下一届通知。把限制写清楚，才能区分真正的未知和还没有做的工作。

版本验收后，阶段性建设任务结束，日常来源巡检继续保留。项目终于有了可以交接的完成状态。

## 9. 上线后的第二轮检查，暴露了使用体验的缺口

验收通过之后，我再次以访问者的方式查看网站，发现了两个很直接的问题：期刊列表显得太长；目录的选择又偏向高分区，Nature、Science 母刊这类综合性期刊也值得补进来。

检查后发现，数据中原本已经存在部分三区、四区记录，Chemical Reviews 也已收录。问题既包括缺少某些期刊，也包括原有准入和筛选范围偏窄，以及浏览方式不够方便。

这轮改进没有停留在回答“可以加分页”，而是形成了六项清单，逐项实现、验证、提交并发布：

| 改进项         | 具体变化                                                                |
| -------------- | ----------------------------------------------------------------------- |
| 期刊分页与范围 | 默认每页 12 本，可选 24／48 本；支持 1—4 区筛选，补入 Nature 和 Science |
| 检索与排序     | 增加名称排序、部分中文别名检索；筛选后保留每页数量，页码回到第一页      |
| 手机筛选       | 筛选区可折叠，结果上方显示当前条件，可逐项取消                          |
| 会议浏览       | 增加分页和未结束／有投稿日期／历史快捷筛选，并修正作者确认事件的分类    |
| 期刊对比       | 可跨页选择最多三本期刊，集中查看范围、索引、分区、投稿要求等信息        |
| 反馈与帮助     | 每条期刊和会议提供预填身份、来源的 GitHub 纠错入口，补充使用说明        |

分页的实现也有几个容易出错的细节：搜索必须作用于整个目录，不能只搜当前页；筛选后要避免停留在不存在的页码；日历导出必须包含完整筛选结果；对比选择不能在翻页之后消失。

这轮还纠正了一个具体的数据语义问题：IEEE MEMS 2027 的作者接受确认事项不应被视作新投稿通道。原始日期与来源保留，事件类型改为确认事项，再验证投稿状态与日历导出的表现。

这让我更明确地感受到，开发时看功能是否存在，使用时看任务能否顺利完成，两者关注的地方并不一样。

## 10. 验证中踩过的坑，比一次通过更值得记录

### 有列表，不代表能搜到用户要的结果

V1.0 界面回归时，“CLEO 2027”搜索曾漏掉真正的当届会议，原因是检索字段没有包含年份。修复后补上了对应回归测试。

这个问题很典型：开发者知道数据已经存在，访问者却只能看到一次没有命中的搜索。关键路径需要用接近真实输入的方式验证。

### 手机布局需要实际查看

移动端曾出现导航撑宽页面的问题；三刊对比加入后，又发现表格将结果列撑出了屏幕。后者通过约束网格列最小宽度、让对比区域独立横向滚动解决。

在 390 px 视口下重新检查文档宽度，才能确认整页不再横向溢出。代码里写了响应式样式，并不等于所有内容长度都能正确适配。

### 工具报错与产品故障要分开判断

一次日历导出测试中，自动化工具等待下载事件超时，但文件实际上已经生成。随后读取文件内容，核对会议事件与时间，才确认导出功能有效。

反过来，命令没有报错也不能替代结果检查。Git 推送成功只说明远程仓库接收了提交，不等于网站已完成部署。

### 本地环境也会引入与业务无关的问题

项目目录改名后，Windows 下部分依赖目录链接仍指向旧位置，影响了本地检查。修复这些链接后，依赖版本和锁文件保持不变。

这类经历提醒我：当 AI 接手排错时，应该先确认问题来自业务逻辑、依赖环境还是工具接口。未经定位就大范围重写代码，可能把一个环境问题变成新的应用问题。

## 11. 发布完成，需要一条可核对的证据链

项目通过 GitHub Actions 检查和发布。主分支更新后，工作流安装锁定依赖，执行数据校验、测试、类型检查与 lint，生成报告，再进行生产构建和 GitHub Pages 部署。

本地验证的核心命令包括：

```bash
pnpm validate:data
pnpm test
pnpm typecheck
pnpm lint
pnpm build
```

由于网站位于 `/optics-scholar-hub/` 子路径，生产构建还需要正确处理资源路径。只在本地根路径打开成功，不能说明部署到 GitHub Pages 后也正常。

最终验收同时查看几个层面：测试是否通过、对应提交的构建与部署是否成功、正式页面是否出现预期功能，以及线上目录摘要是否与本地一致。数据摘要可以核对目录版本，但界面代码是否更新，仍要结合提交、部署和实际页面检查。

截至 2026 年 10 月 10 日本轮完成时，网站的快照是：

| 项目         | 当前结果                               |
| ------------ | -------------------------------------- |
| 正式期刊     | 114 本                                 |
| 会议届次     | 133 届                                 |
| 稳定会议系列 | 98 个                                  |
| 展会与论坛   | 10 项                                  |
| 自动测试     | 41 项通过                              |
| 使用体验改进 | 六项逐项完成并发布                     |
| 访问方式     | 公开的 GitHub Pages 地址，无需站内账号 |

这些数字对应这一轮发布，不代表完整覆盖了光学领域，也不意味着所有期刊的每一年度分区都已核实。新增 Nature、Science 的历史版本分区与当前索引核验仍分别记录，缺口继续明确显示。

## 12. 再做一次，我会怎样与 AI 协作

这次项目让我更愿意把 AI 看成可以连续执行具体工作的协作者。它能快速组合界面、落实规则、编写校验脚本、整理资料和运行检查；但目标是否合理、数据表达是否误导、完成条件是否清楚，仍然需要持续判断。

如果重新开始，我会更早做五件事。

**第一，先给出具体使用任务。** 例如“搜索一个研究方向，筛选某版本分区，比较三本期刊，再打开作者指南”。这样的任务比“做一个完善的网站”更容易验收。

**第二，在收集数据前规定未知值和证据字段。** 后期补来源、拆分年份与学科，比一开始明确模型更容易产生返工。

**第三，把每轮范围写成有限清单。** AI 很容易持续找到可以继续做的事；需要提前区分本轮必须完成的内容与未来维护事项。

**第四，让改进与验证成对出现。** 日期规则变化要验证状态和时区；分页变化要验证筛选、末页和导出；新增对比要验证跨页、数量上限和手机布局。验证应围绕可能出错的行为展开。

**第五，把续接依据留在仓库。** 对话适合提出需求和讨论，但长期状态应该落在数据、提交、证据文档和验收记录中。后续继续工作时，才能知道什么已经完成、什么仍然未知，避免重新绕一遍。

项目也还有可改进的地方：当前数据仍是精选目录，部分来源存在访问限制；没有跨设备关注同步；日历是静态导出；构建中还保留了较大资源块的提示。以后可以根据真实使用反馈决定是否进一步优化性能、补充数据或增加订阅能力。这些是后续选项，不是这一版已经实现的功能。

现在，我可以把网站链接发给同学，让他们直接查期刊、看会议和比较投稿准备；也可以根据具体反馈定位到某个条目、某段逻辑或一次提交。相比最初只有“把信息整理到一起”的想法，项目已经形成了从资料到页面、从问题到修复、从修改到发布的完整过程。

对我来说，这次 AI 辅助开发最有价值的成果，除了一个可以访问的网站，还有一套以后仍然能用的工作方式：把需求写具体，让证据留得住，让每次改动都有可检查的结果，并在一轮目标达成时结束建设。
